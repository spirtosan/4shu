## Open Questions

- **T5 Phase 2 Block A.1 — both format decisions RESOLVED (2026-07-02).** Was two
  unconfirmed Block A assumptions (see prior revision of this file for the original
  writeup); now locked and written into `SPEC_T5.md` v2 §3b, §3d, §5 item 7:
  1. **Poll meta placement — CONFIRMED as built.** Meta (`question`/`mode`/`status`)
     stays as its own `kind:"meta"` list item, packed into `text`, same convention
     as options/ballots. Rationale: Phase 1 added no server-side poll-type column or
     envelope field, and Phase 2 must not touch the server, so `list_items` is the
     only available carrier. No code change needed — this confirmed what was
     already shipped.
  2. **Ballot `item_id` — CHANGED from the Block A assumption.** Was raw username;
     now `"ballot:" + username`. `PollParser.kt` derives `voterId` by stripping only
     the leading `"ballot:"` occurrence (usernames may contain `:`, so no split-on
     `:`). Meta/option id schemes are untouched — namespacing ballots alone already
     guarantees no user-derived string collides with the meta id or any option id in
     the `(list_id, item_id)` PK. Still stable per-voter, still plaintext to the
     server (`ballot:alice` visible at rest/on the wire), upsert key is the opaque
     full string → no server/schema/protocol change.
- **T5 — design RESOLVED** (planning chat + recon, 2026-07-02): see `SPEC_T5.md` v2 for the full decision log (single/multi at creation, named-only votes, client-honored close, re-vote-by-upsert, live results via `list-state`, generic offline queue). Server Phase 1 (group-aware lists) implemented this session; Phase 2 (client poll UI) not started.
- **T5 Phase 2 Block D read-step — list-create atomicity CONFIRMED (2026-07-02).** Investigated
  before writing any send code, per the block's stop-and-report gate. `list-create` already
  carries the full `items` array inline in one message (`ChatViewModel.createList()`,
  `server.js` `case 'list-create'` loops the whole array before its single `broadcastListState`
  call) — no follow-up `list-edit`, no per-item round trip, no server change needed. Meta +
  every option ship as one atomic unit through the existing todo-list wire path; the "Poll
  unavailable" partial-render Block B guards against structurally cannot happen via creation.
- **T5 Phase 2 Block D — group list-state bug found + fixed (2026-07-02, client-only, not a
  server change).** While wiring group poll creation, found `FshuService.persistListState`
  unconditionally required a `to` field (`?: return`) before doing anything else. The server
  sends `to: null` for group lists (`list.peer` is unset — group lists key off `groupId`
  instead, per Phase 1), and `null` is not `isJsonPrimitive` in Gson, so **every group
  list-state push — including updates to lists members already knew about — was silently
  dropped client-side.** This was Phase 1 dead code: server-side group-aware lists shipped
  2026-07-02 but nothing client-side had exercised group list-create until this block, so the
  bug was never hit. Fixed by making `to` conditionally required (only on the DM path;
  group lists key off `groupId`, mirroring `persistGroupMessage`'s `from=owner/to=""/groupId`
  convention) and moving the check below the version-staleness short-circuit so updates to
  known lists aren't gated on it either. Notification path also branched: group lists now use
  `notifyGroupMessage` (mute-respecting, matches how regular group messages notify) instead of
  the DM-shaped `MessagePopupActivity`/`notifyMessage` pair. No server/protocol/schema change —
  purely a client-side parsing bug. This was necessary for Block D's own "create in a group,
  confirm it propagates and renders on another member's phone" test criterion to be reachable
  at all; without it, group poll creation would appear broken in exactly the way Block D was
  being tested for, but the root cause would've been Phase 1, not Block D.
- **T5 Phase 2 Block D — option_id scheme.** `"opt-<index>"` in creation-display-order (0..N-1),
  used as both the packed `option_id` field ballots reference and the outer list-item `id`.
  Collision-free by construction: sequential indices are unique within one creation call and
  can't collide with the reserved literal `"meta"` id or the `"ballot:"` namespace (Block A.1).
- **T5 Block D follow-up — chat-list preview bugs fixed; live-refresh gap found + flagged, NOT
  fixed (2026-07-02, stop-and-report — decision pending).** Fixed: DM preview mislabeled polls
  as "Todo list" (`MainActivity.kt:700`); group preview dumped raw items-array JSON for any list
  type (`MainActivity.kt:737-741`, no `"list"` branch existed — pre-existing gap for group todo
  lists too, never hit before Block D made group list-create reachable). Both fixed via a shared
  `isPollItemsJson()` helper mirroring `ChatAdapter.bindListOrPoll`'s detection. **Found but left
  alone per the stop-and-report rule:** group list/poll creation never triggers a live chat-list
  refresh — `group-preview-update` (what `enrichGroupItems()` listens for) is only emitted from
  `persistGroupMessage`, not `persistListState`. So even with the preview text now correct, a
  group poll's entry may not update in the chat list until some unrelated event (e.g. another
  group message) triggers a refresh. Client-only fix if wanted (add the same emit to
  `persistListState`'s group branch) — deferred pending a decision on priority/scope, not bundled
  into this fix.
- **T5 Phase 2 Block D.1 — poll creation gated to groups only (product decision, Ivan
  2026-07-02, RESOLVED).** T5's scope is "polls in groups" — DM poll creation was incidental,
  a side effect of polls riding the todo-list infrastructure. "New poll" (`action_new_poll`)
  now shows only when `groupId != null`, mirrored exactly off `action_new_todo`'s existing
  `!isGroupChat` gate (`ChatActivity.onPrepareOptionsMenu`). **This blocks creation only** —
  `PollParser`, `ChatAdapter.bindListOrPoll`, `persistListState`'s DM/group branching, and the
  DM poll-preview fixes all stay untouched and DM-capable, so a poll that ever reaches a DM
  context (old data, a future feature) still renders correctly rather than mislabeling or
  crashing. Comment left at the gate site so this isn't "simplified" away later.
- **T5 Block D.1 — preview-string sweep (2026-07-02).** Grepped `app/src` for every hardcoded
  "Todo list"/📝 list-preview literal to catch remaining copies of the bug fixed piecemeal across

- **server.js repo/live drift (found 2026-07-02) — RESOLVED (2026-07-03).** The committed
  `server.js` and the deployed `/opt/fshu5/server.js` had diverged (full history: read-only
  recon in `./_recon_2026-07-03/RECON_REPORT.md`, then this reconciliation). **Resolution:
  repo `server.js` adopted live verbatim, sha256-proven identical to both the live pull and
  the `snapshots/live-2026-07-02/server.js` capture** (no hand-merge — see Changelog for hash).
  This drops `trust_level` column + family-group trust propagation + `admin-set-trust` (repo

  — see Dropped, above) and adopts every live-only safety feature into git in one move:

  `hide_presence` (correcting this note's prior wording — it's a **`users`-table** column, not
  a per-contact setting), `group-file` binary upload groupId support, and group-key
  self-healing on connect. DB schema unchanged throughout (`schema.live.sql` ==
  `snapshots/live-2026-07-02/schema.sql`, byte-identical; `trust_level` was never a live DB
  column, so no migration was needed either direction). Syntax-validated on the live runtime
  via a `/tmp` candidate file (`node --check`, deleted after) — production `/opt/fshu5/`
  itself was never touched or restarted. **One inert residual remains in live**, harmless and

  anywhere in live (it's a leftover from before trust_level was fully backed out live-side) —

  and `patch_server.py` (both tracked in git, both contain the now-dropped trust_level system)
  removed 2026-07-03 (git history preserves them) — see changelog.
- **T5 Block C.1 — same race class in the todo path, flagged not fixed (found 2026-07-02).**
  `ChatViewModel.checkItem`/`editList` (DM todo checkboxes/bulk-edit) share the identical
  read-modify-write-then-send pattern that caused the poll stuck-tally bug: read `content` →
  send → optimistic `updateContent` on a stale/pre-send snapshot, unguarded against
  `FshuService.persistListState`'s echo write. Not folded into C.1 per instruction — todo lists
  are DM-only (peer-to-peer, no group fan-out, so no self-echo path the way group polls have) and
  this is pre-existing behavior, not a C regression. Lower likelihood, same underlying class.
  **If wanted later:** routing `checkItem`/`editList`'s optimistic writes through the same
  `ListWriteLock.mutex` (re-reading fresh content inside the lock, mirroring `voteOption`'s C.1
  fix) would be behavior-neutral and mechanically trivial — not done here, not requested.
- **T5 Block C.1 — residual race flagged 2026-07-02, RESOLVED in Block C.2 (2026-07-02).**
  `FshuService.handleListAck` wrote `listVersion` alone via `messageDao().updateListVersion`,
  racing `persistListState`'s echo for the same edit (both dispatched on independent coroutines
  with no ordering guarantee) — if the ack-only bump landed first, the echo's own
  `version <= existing.listVersion` guard saw `V <= V` and silently dropped the authoritative
  content, stranding a device without a concurrent voter's ballot until a later edit. See Block
  C.2 changelog entry for the fix and verification.
