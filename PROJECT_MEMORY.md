## Open Questions

- **T5 Phase 2 Block A.1 — both format decisions RESOLVED (2026-07-02).** Was two
  unconfirmed Block A assumptions (see prior revision of this file for the original
  writeup); now locked and written into `SPEC_T5.md` v2 §3b, §3d, §5 item 7:
  1. **Poll meta placement — CONFIRMED as built.** Meta (`question`/`mode`/`status`)
     stays as its own `kind:"meta"` list item, packed into `text`, same convention
     as options/ballots. Rationale: Phase 1 added no server-side poll-type column or
     envelope field, and Phase 2 must not touch the server, so `list_items` is the
     only available carrier. No code change needed — this confirmed what was
     already shipped.
  2. **Ballot `item_id` — CHANGED from the Block A assumption.** Was raw username;
     now `"ballot:" + username`. `PollParser.kt` derives `voterId` by stripping only
     the leading `"ballot:"` occurrence (usernames may contain `:`, so no split-on
     `:`). Meta/option id schemes are untouched — namespacing ballots alone already
     guarantees no user-derived string collides with the meta id or any option id in
     the `(list_id, item_id)` PK. Still stable per-voter, still plaintext to the
     server (`ballot:alice` visible at rest/on the wire), upsert key is the opaque
     full string → no server/schema/protocol change.

- **T5 Phase 2 Block D read-step — list-create atomicity CONFIRMED (2026-07-02).** Investigated
  before writing any send code, per the block's stop-and-report gate. `list-create` already
  carries the full `items` array inline in one message (`ChatViewModel.createList()`,
  `server.js` `case 'list-create'` loops the whole array before its single `broadcastListState`

- **T5 Phase 2 Block D — group list-state bug found + fixed (2026-07-02, client-only, not a
  server change).** While wiring group poll creation, found `FshuService.persistListState`
  unconditionally required a `to` field (`?: return`) before doing anything else. The server
  sends `to: null` for group lists (`list.peer` is unset — group lists key off `groupId`
  instead, per Phase 1), and `null` is not `isJsonPrimitive` in Gson, so **every group
  list-state push — including updates to lists members already knew about — was silently
  dropped client-side.** This was Phase 1 dead code: server-side group-aware lists shipped
  2026-07-02 but nothing client-side had exercised group list-create until this block, so the
  bug was never hit. Fixed by making `to` conditionally required (only on the DM path;
  group lists key off `groupId`, mirroring `persistGroupMessage`'s `from=owner/to=""/groupId`
  convention) and moving the check below the version-staleness short-circuit so updates to
  known lists aren't gated on it either. Notification path also branched: group lists now use
  `notifyGroupMessage` (mute-respecting, matches how regular group messages notify) instead of
  the DM-shaped `MessagePopupActivity`/`notifyMessage` pair. No server/protocol/schema change —
  purely a client-side parsing bug. This was necessary for Block D's own "create in a group,
  confirm it propagates and renders on another member's phone" test criterion to be reachable
  at all; without it, group poll creation would appear broken in exactly the way Block D was
  being tested for, but the root cause would've been Phase 1, not Block D.
- **T5 Phase 2 Block D — option_id scheme.** `"opt-<index>"` in creation-display-order (0..N-1),
  used as both the packed `option_id` field ballots reference and the outer list-item `id`.
  Collision-free by construction: sequential indices are unique within one creation call and
  can't collide with the reserved literal `"meta"` id or the `"ballot:"` namespace (Block A.1).
