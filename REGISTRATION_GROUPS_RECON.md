## A. Profile registration (new-user creation)

**This is not an in-app flow at all.** `LoginActivity` has no registration UI or
code path — it only logs in with an existing username/password
(grep for "register" in `LoginActivity.kt` returns nothing but an unrelated
comment). Account creation happens entirely through the server's built-in HTTP
pages, outside the APK.

- **Entry point:** a human clicks an invite link `https://.../fshu5/invite/<token>`
  (generated by an admin — see Flow G). `handleHttp` (`server.js:1243`) serves:
  - `GET /invite/:token` (`server.js:1247`) — looks up the token via
    `stmt.getInvite`, 404s with "Link expired or invalid" if missing/used/expired,
    otherwise renders an HTML registration form
    (username/email/password/confirm/secret question/secret answer).
  - `POST /register` (`server.js:1281`) — the form target. Re-validates the
    invite (same expiry/used check, so a link can't be raced), validates
    username (`^[a-zA-Z0-9_]{3,20}$`, case-folded to lowercase for storage),
    password length ≥6 and matches confirm, email format + uniqueness, username
    uniqueness, secret question (≥5 chars) + secret answer (≥3 chars).
  - On success: `bcrypt.hash` on both password and secret answer,
    `stmt.insertUser.run(...)`, then `stmt.useInvite.run(u, now, token)` marks
    the invite consumed. Renders a static "Account created, download the app"
    page.
- **Server handler:** no WS `case` at all — purely `handleHttp`, plain
  `http.createServer`, hand-rolled form/urlencoded/JSON body parsing (no
  Express).
- **DB effect:** `users` row inserted (`username, password_hash, created_at,
  email, secret_question, secret_answer_hash`); `invites.used_by` /
  `invites.used_at` set on the consumed token.
- **Client/Room effect:** none — the phone isn't involved until the human
  separately opens the app and logs in with the new credentials via the normal
  `auth` WS message.
- **Repo vs. live:** `invites` and `users` table shapes are byte-identical
  between committed `server.js`'s inline `CREATE TABLE` and
  `snapshots/live-2026-07-02/schema.sql` (extra `users` columns like `email`,
  `discoverable`, etc. come from idempotent `ALTER TABLE ... ADD COLUMN`
  statements at `server.js:339-349`, present in both — not drift, just
  post-baseline migrations).

**Friction / simplification candidates:**
- Registration living entirely outside the Android app, as raw hand-rolled HTTP
  form parsing (no framework, manual `body.split('&')` parsing duplicated
  across 6+ handlers in `handleHttp`), is easy to overlook when reasoning about
  "the app" — it's really a second, tiny web app bolted onto the WS server.
- The same manual form-parsing block is copy-pasted in `/register`, `/reset`,
  `/reset/confirm`, `/reset/question`, `/reset/question/verify` (5 copies of
  the same 8-line loop). Candidate for a shared `parseFormBody(req)` helper.
- `/reset` page (`server.js:1374`) has a garbled label `??? or ???` — pre-existing,
  already tracked as **T1** (parked, low priority) in `PROJECT_MEMORY.md`. Not
  re-flagging as new.

**Open questions for Ivan:**
- Is it intentional that registration has zero Android-side involvement (no
  deep link back into the app, no "open app" button after "Account created")?

## B. Group creation

- **UI entry point:** `MainActivity` overflow menu → `action_new_group`
  (`MainActivity.kt:233`) → `showNewGroupDialog()` (`MainActivity.kt:421`). Name
  field + checkbox list of **existing contacts only** (`users.filter {
  !it.isGroup }` — this is the same list backing the main chat list, i.e.
  accepted contacts, not a fresh search).
- **Client code path:** `createGroup()` (`MainActivity.kt:482`) generates a
  random AES group key client-side (`CryptoHelper.generateGroupKey()`), a
  random `groupId` (UUID), and for every selected member + self, ECDH-encrypts
  the group key to that member's known public key
  (`CryptoHelper.encryptGroupKeyForMember`). Sends one `group-create`:
  `{groupId, name, groupType:"group", members:[{username, encryptedKey}]}`.
  Members whose public key isn't cached yet get `encryptedKey: ""`.
- **Server handler:** `case 'group-create'` (`server.js:2494`). Validates every
  named member exists (`user-not-found:<name>` error otherwise), inserts the
  `groups` row (`stmt.createGroup`, owner = creator), inserts one
  `group_members` row per member (creator as `role:'owner'`, rest as
  `'member'`), then `broadcastGroupState(groupId)` pushes a `group-state` to
  every member (online: direct send; offline: `enqueue`).
- **DB effect:** 1 row in `groups`, N rows in `group_members`.
- **Room effect:** every member's client receives `group-state` →
  `FshuService.handleGroupState()` (`FshuService.kt:1856`) upserts the `Group`
  row, decrypts its own `encryptedGroupKey` slot (ECDH using the owner's public
  key + own private key) and stores the plaintext `groupKey` locally, then
  **wipes and fully re-inserts** all `GroupMember` rows for that group
  (`removeAll` + `upsertAll`, not a diff/merge).
- **Repo vs. live:** `group-create` handler and `groups`/`group_members` schema
  match the live snapshot verbatim — no drift.

**Friction / simplification candidates:**
- A member with no cached public key silently gets `encryptedKey: ""` sent to
  the server (not blocked client-side) — that member will be stuck until the
  `group-key-needed` self-healing path kicks in (see Flow D). Works, but the
  failure is invisible at creation time (no warning shown to the creator).
- `handleGroupState`'s "delete all members, re-insert all members" pattern
  repeats for every single group event (create/invite/kick/leave/rename/promote
  all call `broadcastGroupState`, and every recipient wipes+reinserts). Correct
  but a full-table churn for what's usually a 1-row delta; a diff-based upsert
  would be more surgical if this ever needs to scale to larger groups.

**Open questions for Ivan:** none new beyond the general note above.

## C. Group find / discovery

**This flow does not exist.** There is no server verb for searching or listing
discoverable groups (`user-search` at `server.js:2776` is users-only — it
matches `users` table, not `groups`), and no Android UI for it: `SearchActivity`
(the only search screen in the app) has zero group-related code. Groups are
invite-only in the strictest sense — the *only* way to end up in a group is (a)
being named as a member at creation time (Flow B) or (b) being individually
added afterward by an owner/admin (Flow D). There is no group code/link, no
public directory, no "browse groups" anywhere.

**Friction / simplification candidates:** N/A — nothing to simplify since
nothing was built. Flagging in case this was assumed to exist somewhere and
silently isn't.

**Open questions for Ivan:**

  this recon task's flow C actually describing the "add contact as new group
  member" step of Flow D? Recommend dropping flow C from future planning docs
  if the latter — right now it reads as a phantom feature.

## D. Group join

There is no self-service "join". The only path a user enters a group after
creation is being **added by an existing owner/admin**:

- **UI entry point:** open the group's chat → overflow → `action_group_info`
  → `showGroupInfo()` (`ChatActivity.kt:1811`). If `isOwnerOrAdmin`, a neutral
  dialog button `btn_add_member` appears → `showAddMemberDialog()`
  (`ChatActivity.kt:2067`), which lists the caller's **accepted contacts** not
  already in the group (`contactDao().getAcceptedContacts(me)` filtered against
  `existingMembers`) — again, contacts only, no free-text/search entry.
- **Client code path:** `addMemberByUsername()` (`ChatActivity.kt:2092`). Reads
  the local plaintext group key from Room, requires the target's cached public
  key (`Prefs.getPeerPublicKey`) — errors out client-side
  (`toast_cannot_invite_no_key`) if absent, unlike group-create's silent
  `encryptedKey:""`. Sends `group-invite: {groupId, username, encryptedKey}`.
- **Server handler:** `case 'group-invite'` (`server.js:2574`). Validates the
  group exists, the sender's `role` is `owner` or `admin`
  (`['owner','admin'].includes`), the invitee exists and isn't already a
  member. Inserts one `group_members` row (`role:'member'`), then
  `broadcastGroupState(groupId)`.
- **DB effect:** 1 new `group_members` row.
- **Room effect:** every member's `handleGroupState` runs (same wipe+reinsert
  as Flow B) — including the new member's own client, which is how it learns
  it was added and gets its `encryptedGroupKey` slot to decrypt the group key.
- **Key-recovery path (`group-key-needed`):** if a member is missing an
  encrypted-key slot (e.g. was added before their public key was known), the
  server can push `group-key-needed` to the owner, who resolves it via
  `handleGroupKeyNeeded()` (`FshuService.kt:2106`) by either regenerating the
  group key (if the owner itself lost it) or re-encrypting the existing key
  for the missing member (`group-key-submit`). This is the self-healing
  mechanism referenced in `PROJECT_MEMORY.md`'s 2026-07-03 reconciliation entry.
- **Repo vs. live:** no drift — `group-invite` handler and schema match.

**Friction / simplification candidates:**
- "Join" is really "invite" from the acting member's perspective — worth
  renaming in any future planning doc to avoid implying a pull-based join flow
  exists (there is only push/add).
- Add-member is contact-list-only, same restriction as group-create; consistent
  at least, so not a bug, just a hard boundary worth being explicit about.

**Open questions for Ivan:** none beyond confirming the naming above matches
intent.

## E. Group leave (and owner-leave / group delete)

- **UI entry point:** `showGroupInfo()` dialog's positive button
  (`ChatActivity.kt:1998-2025`): label and action depend on `myRole`.
  - `myRole == "owner"` → button is **"Delete group"** → sends `group-delete`.
  - otherwise → button is **"Leave group"** → sends `group-leave`.
  - Menu-level gating mirrors this: `action_leave_group` is only visible when
    `isGroupChat && !isOwner`; `action_delete_group` only when
    `isGroupChat && isOwner` (`ChatActivity.kt:1002-1003`).
  - **There is no "owner leaves" path in the UI at all** — an owner physically
    cannot leave without deleting the whole group (see below for what the
    server does if this were ever attempted another way).
- **Client code path (leave):** just sends `{type:"group-leave", groupId}`.
  **Client code path (delete):** just sends `{type:"group-delete", groupId}`.
- **Server handler — `group-leave`** (`server.js:2617`): finds caller's
  membership; **if `role === 'owner'`, rejects with `group-error
  reason:"owner-cannot-leave"`** — this is the actual server-side enforcement
  of "owner can't leave," independent of the UI hiding the option. Otherwise
  `removeGroupMember`, notifies the leaver's own other devices
  (`group-removed reason:"left"`), then `broadcastGroupState` to the rest.
- **Server handler — `group-kick`** (`server.js:2596`, reachable only from the
  member-list "Remove" button, owner/admin-gated): same shape, but also
  explicitly blocks kicking the owner (`reason:"cannot-kick-owner"`).
- **Server handler — `group-delete`** (`server.js:2633`): requires
  `group.owner === username` (hard equality, not role-based — an `admin` can
  never delete, only the literal owner). Deletes all `group_members` rows then
  the `groups` row itself (`stmt.deleteGroupMembers`, `stmt.deleteGroup`), and
  pushes `group-removed reason:"deleted"` to every former member (online direct,
  offline enqueued).
- **DB effect:** leave/kick → 1 `group_members` row removed. delete → all
  `group_members` rows for the group + the `groups` row removed.
- **Room effect:** `handleGroupRemoved()` (`FshuService.kt:2041`) on every
  affected device: deletes the local `Group` row (cascades to local
  `GroupMember` rows via the `onDelete = CASCADE` foreign key — server-computed
  deletion, not a second wipe call) and all local group messages
  (`deleteMessagesForGroup`), then shows a notification distinguishing
  "removed" / "deleted" / "left" by `reason`, unless `ChatActivity` is already
  open.
- **What actually happens if the owner "leaves" (there is no route to this,
  confirmed both ways):** UI never offers it; server explicitly rejects
  `group-leave` from an owner. The **only** way a group with an owner stops
  existing is the owner explicitly choosing "Delete group" (which removes it
  for everyone, not just the owner) or **promoting someone else to owner
  first** via `group-promote` — but that verb is unreachable from the client
  (see Flow F) — so in practice, today, **an owner is permanently stuck as
  owner until they delete the whole group.** There is no ownership-transfer UI.
- **Repo vs. live:** no drift — handlers and schema match.

**Friction / simplification candidates:**
- **Owner lock-in is the single biggest finding of this recon.** An owner who
  wants to step back (e.g. hand the group to someone else and leave) has no
  client-side path to do so — `group-promote(role:"owner")` exists
  server-side and correctly demotes the old owner to `admin` and reassigns
  `groups.owner`, but nothing in the app ever sends it. Today "leave" for an
  owner is a dead end.
- `group-kick`/`group-leave`/`group-delete` are three separate, mostly
  parallel code paths (each re-fetches members, re-checks role, re-broadcasts)
  that could plausibly share more, but that's a minor efficiency note, not a
  bug.

**Open questions for Ivan:**
- Is owner-can't-leave-without-deleting intentional (safety: no orphaned
  group), or is ownership transfer a gap that should be closed (expose
  `group-promote` in the group-info dialog)? This feeds directly into Flow F.

## F. Admin rights via the group-info dialog

**Confirmed exactly as the prior memory note suspected: the `admin` group role
is fully supported server-side and rendered client-side, but is unreachable —
nothing in the app can ever promote a member to `admin`.**

- **Role storage:** `group_members.role` (`TEXT DEFAULT 'member'`), values used
  by the server are `'owner' | 'admin' | 'member'`. Role is set at
  `group-create` (creator → `owner`, everyone else → `member`) and at
  `group-invite` (new members always → `member`). **The only place `role`
  ever changes after that is `group-promote`** (`server.js:2693`).
- **Role-gated server actions today** (all check `['owner','admin'].includes(role)`
  unless noted):
  - `group-invite` (add member)
  - `group-kick` (remove member, also blocks targeting the owner)
  - `group-rename`
  - `group-key-rotate`
  - `group-key-submit`
  - `group-promote` to `admin`/`member` (owner *or* admin can do this);
    promote to `owner` requires the sender to already be `owner`
    (`server.js:2702-2706`, and correctly demotes the old owner to `admin` as
    part of the same transaction).
  - `group-delete` is **not** role-gated the same way — it's a strict
    `group.owner === username` check, so an `admin` can do everything above
    but still can't delete the group.
- **Client-side reachability of `admin`:** grepped the entire Android app for
  `group-promote` — **zero matches**. The group-info dialog
  (`ChatActivity.kt:1811`) computes `isOwnerOrAdmin` and:
  - shows the role icon for existing admins (⭐, vs 👑 for owner) — so if a row
    ever has `role:"admin"` (only possible via `admin.js`... actually see
    below — not even that), it displays correctly,
  - gates "change photo", "rename", "add member" on `isOwnerOrAdmin`,
  - gates "remove member" (kick) button per-row on `isOwnerOrAdmin`,
  - **never exposes a promote/demote action** — there's no UI element anywhere
    that lets an owner turn a member into an admin. The dialog's neutral/
    positive buttons are only "Add member" and "Delete group"/"Leave group".
- **Is `admin.js` (the CLI) the same code path?** No — confirmed separate.
  `admin.js` only has `add/remove/reset/list/setadmin/removeadmin`, all
  operating on the **`users.admin`** column (site-wide admin — grants access
  to the in-app Admin Panel / `admin-*` WS verbs). It has no concept of
  `group_members.role` at all — it cannot create a group admin either. The
  two "admin" concepts (`users.admin` = site admin, `group_members.role =
  'admin'` = group admin) are completely independent systems that happen to
  share the English word "admin."
- **Net effect:** in the shipped app today, every group has exactly one
  `admin`-eligible action-holder in practice — the `owner` — because no code
  path ever writes `role = 'admin'` into `group_members`. The `admin` role
  value, the ⭐ icon, and every `['owner','admin']` check server-side are all
  live but permanently unexercised.

**Friction / simplification candidates:**
- Two honest paths forward, not evaluated further per this recon's scope:
  (a) ship a promote-to-admin action in the group-info dialog to actually use
  the role, or (b) if group-admin was never going to be used, this is a fair
  amount of dead-but-correct code (one role value, one icon branch, 4 role
  checks server-side) that could be simplified to a plain owner/member binary.
  Given Flow E's owner-lock-in finding, option (a) (specifically enabling
  `group-promote(role:"owner")` for ownership transfer) looks like the more
  useful of the two — but that's a product call, not made here.

**Open questions for Ivan:**
- Do you want group-admin to become a real, reachable role (promote/demote UI),
  or should it be stripped back to owner/member only? This decision also
  resolves Flow E's owner-lock-in gap if you choose "make it reachable" (adding
  a "Transfer ownership" action would need nothing new server-side).

## G. Registration/invite-link lifecycle

- **What generates a link:** `AdminPanelActivity` → "Generate invite" button
  (`generateInvite()`, `AdminPanelActivity.kt:185`) → sends
  `admin-invite-create` (no payload). **Only site-admins can do this** — gated
  both by the client only showing the Admin Panel menu item when
  `Prefs.isAdmin(this)` (`MainActivity.kt:223`) and, authoritatively, by the
  server re-checking `stmt.getUser.get(username)?.admin` inside the handler
  (`server.js:2369`) before doing anything.
- **Where it's stored:** `invites` table (`token PRIMARY KEY, created_by,
  used_by, expires_at, used_at`). `case 'admin-invite-create'`
  (`server.js:2369`) creates `token = crypto.randomBytes(24).toString('hex')`,
  `expires_at = now + 48h` (hardcoded, matches "invite links (48h)" in
  `PROJECT_KNOWLEDGE.md` §8), inserts the row, replies
  `admin-invite-created {token, url, expiresAt}`.
- **How it expires:** purely a timestamp comparison at **read time** — there is
  no cron/sweep job that deletes expired rows. Every consumer
  (`GET /invite/:token` at registration time, and implicitly nothing else)
  re-checks `!invite || invite.used_at || (invite.expires_at && invite.expires_at
  < now)` itself. **The row is never deleted for being expired** — only
  `admin-invite-revoke` (`server.js:2388`, `DELETE FROM invites WHERE token = ?
  AND used_at IS NULL`) or being consumed (`used_by`/`used_at` set) changes an
  invite's state at all.
- **Confirmed: expired-but-unused links do remain visible in the admin panel.**
  Root cause is two independent gaps that compound:
  1. **Server** `stmt.listInvites` (`server.js:462`): `SELECT token,
     created_by, expires_at, used_by, used_at FROM invites ORDER BY rowid DESC
     LIMIT 50` — **no `WHERE` clause at all.** It returns the 50 most recent
     invites regardless of used or expired state.
  2. **Client** `updateInviteList()` (`AdminPanelActivity.kt:227`) filters out
     only invites where `used_by != null` (i.e. hides *used* invites) — it
     never compares `expires_at` against the current time. So an invite that
     is unused but past its 48h window sails through both filters and shows up
     in the admin list indefinitely (or until it ages out of the 50-row
     window, or an admin manually hits "Revoke").
  - The revoke button works correctly regardless (`DELETE ... WHERE used_at IS
    NULL`, so it can revoke an expired-but-unused row fine) — the only gap is
    that expired rows aren't *distinguished or auto-hidden* in the list.
- **DB effect summary:** create → 1 `invites` row. register (Flow A) → same row
  gets `used_by`/`used_at` stamped. revoke → row hard-deleted (only if
  unused). Nothing ever auto-deletes on expiry.
- **Repo vs. live:** `invites` schema and every handler above (`admin-invite-*`,
  `/invite/:token`, `/register`) match `snapshots/live-2026-07-02` byte for
  byte — no drift.

**Friction / simplification candidates:**
- Cheapest fix (not applied, per this session's read-only scope): either (a)
  add `WHERE used_at IS NULL AND (expires_at IS NULL OR expires_at > ?)` to
  `stmt.listInvites` and pass `Date.now()`, or (b) keep the server dumb and add
  an `expires_at < now` check next to the existing `usedBy` filter in
  `AdminPanelActivity.updateInviteList()`. Either is a small, isolated change;
  (a) is probably the more correct fix since a second admin client (if one
  ever exists) would inherit the bug otherwise.
- No visual distinction in the admin list between "active" and "expired" rows
  even if they were shown deliberately — `tvExpiry` just prints the date, no
  color/label change for "already past."

**Open questions for Ivan:**
- Want expired-unused invites hidden entirely, or shown but visually marked
  "expired" (in case you want to re-issue/reference the token for support
  purposes)? Determines whether the fix is a server filter or a client label.

## Summary of cross-flow findings

1. **Flow C doesn't exist** — no group discovery/search anywhere.
2. **Flow E/owner-leave gap** — owners cannot leave or transfer ownership;
   `group-promote(role:"owner")` exists server-side but is never called from
   the client.
3. **Flow F confirms the memory note** — group `admin` role is fully wired
   server-side (4+ role-gated actions, correct promote/demote logic, live UI
   rendering of the role icon) but is completely unreachable — no client code
   path ever sends `group-promote`.
4. **Flow G confirms Ivan's observation** — expired-but-unused invite links
   remain visible in the admin panel because neither the server's
   `listInvites` query nor the client's `updateInviteList()` filters on
   `expires_at`; only `used_at` is checked (client-side only).
5. **No repo/live drift found** in any table or handler touched by flows A–G —
   consistent with the 2026-07-03 reconciliation already recorded in
   `PROJECT_MEMORY.md`.
